# 全局工时管理页面 Spec

## 背景

当前工时数据分散在任务、需求、Bug 等对象上。管理者需要的不是一个可任意切换但反馈不明显的“分析维度”表格，而是一个固定、可解释、可追溯的全局工时管理页面，用来观察团队投入结构、进度/成本压力、人员负载和早期风险。

## 管理目标

1. 从空间、时间、人员三个维度筛选工时范围。
2. 看到选定范围内总消耗工时、实际/预估工时、研发对象投入比例。
3. 识别长期没有更新工时的产品、项目、迭代或具体研发对象。
4. 看到每个人的工时总量，以及其工时在不同对象类别或空间范围上的分布。
5. 在总览、图表和明细之间快速追溯，定位具体工时记录和工作内容。

## 页面入口

1. 页面入口为 `BI -> 全局工时`。
2. 页面必须使用禅道 zin UI 渲染路径，保持和 `BI -> 大屏` 一致的顶部导航、面包屑、`#main/#mainContent` 结构。

## 筛选模型

页面不再提供“分析维度”下拉框。页面固定展示总览指标、对象分布、停滞对象、人员分布和工时明细。

### 空间维度

1. 产品线、产品。
2. 项目集、项目。
3. 迭代/执行。
4. 研发对象类型：
   - 业务需求：`epic`
   - 用户需求：`requirement`
   - 研发需求：`story`
   - Bug：`bug`
   - 任务：`task`
   - 其他：其他对象类型
5. 研发对象 ID：支持按具体对象 ID 过滤。
6. 关联对象：
   - 默认不包含关联对象工时。
   - 勾选后，按具体需求/Bug 过滤时，需要将其关联任务上的工时一并纳入统计。
   - 第一阶段至少支持通过 `zt_task.story` 将需求关联任务工时纳入统计。

### 时间维度

1. 动态时间：
   - 本周
   - 本月
   - 本季度
2. 自定义时间段：
   - 开始日期
   - 结束日期
3. 动态时间和自定义时间同时存在时，以自定义时间段为准。

### 人员维度

1. 部门。
2. 团队。
3. 具体成员。
4. 当前实现中，部门基于 `zt_user.dept`；团队优先保留筛选位，第一阶段可按项目/执行团队扩展。

### 明细二次过滤

工时明细在全局筛选范围内支持进一步按以下字段收窄：

1. 某一天。
2. 人员。
3. 产品。
4. 项目。

## 总体指标

1. 总消耗工时：
   - 当前筛选范围内所有工时记录 `consumed` 求和。
2. 实际消耗工时/预估总工时：
   - 只统计设置了预估工时的对象。
   - 任务优先使用 `zt_task.estimate`。
   - 需求/Bug 的预估字段如果当前表结构存在则纳入，否则不进入分母。
3. 研发对象分布比：
   - 按业务需求、用户需求、研发需求、Bug、任务、其他汇总工时占比。
   - 用单条横向堆叠长条展示，不同对象类别使用不同颜色。
4. 停滞对象：
   - 停滞阈值可设置，默认 5 天。
   - 对同一对象在筛选时间范围内的工时日期排序。
   - 任意两条工时记录间隔超过阈值，或最后一条工时记录到筛选结束日期超过阈值，视为停滞。
   - 用横向长条图展示，条长表示停滞天数，对象名显示为对象类型和对象 ID；具备名称时显示名称。

## 人员工时分布

1. 以人员为行展示横向堆叠条。
2. 右侧显示该人员总工时。
3. 堆叠段默认按研发对象类别着色。
4. 颜色口径与研发对象分布比一致。
5. 数据来自当前筛选范围。

## 工时明细

1. 明细列包括日期、产品、项目、迭代、对象类型、对象 ID、人员、耗时、剩余、工作内容。
2. 工作内容可直接完整查看，不能只截断后无法访问。
3. 明细受全局筛选和明细二次过滤共同约束。
4. CSV 导出使用当前全局筛选和明细二次过滤后的明细。

## 数据源和口径

1. `zt_effort` 为基础工时来源。
2. 如果 `zt_objecteffort` 存在，则合并其记录。
3. 只统计未删除记录：`deleted = 0` 或 `deleted = '0'`。
4. 对象类型归一化：
   - `epic` -> 业务需求
   - `requirement` -> 用户需求
   - `story` -> 研发需求
   - `bug` -> Bug
   - `task` -> 任务
   - 其他 -> 其他
5. 产品字段可能是字符串，统计时取可转换的产品 ID。
6. 项目、执行、人员字段按记录字段归集。
